2 Executive Summary
Our group acted as a Database Security Engineering Team for a university research office. We designed and
built a database-backed information system, the University Research Grant Management System, that carries a
research grant through its whole life cycle: call for proposals, proposal, peer review, funding decision and audit.
The system holds information that is worth attacking: unpublished research, confidential reviewer comments,
credentials, public money and a security audit trail. We then followed the process required by the assignment –
Design → Build → Assess → Attack → Test → Secure → Monitor → Recover → Harden → Investigate → Report
– and the report is organised in the 22 sections the instructor prescribed.
Approach. Security is enforced in three independent layers, so that a mistake in one does not open the data: (1)
the PHP application checks a role permission on every route and every operation; (2) PostgreSQL itself refuses
what the role may not do, through a non-owner runtime account, column-level privileges, row-level security (RLS)
and guard triggers, and it verifies who is acting through a signed actor token instead of believing the application;
(3) the surrounding environment is hardened (private network, TLS, read-only code, encrypted backups). Money
is the most sensitive integrity asset, so every award is a single database function that locks the grant call, re-checks
eligibility and limits, and writes the decision, the budget change, the status change and the audit event together.
Officers and auditors must also present a second factor (TOTP).
Attack and remediation. We attacked our own system in an isolated lab on 11 November 2026 (115 baseline
checks resisted, 5 findings F01–F05, 3 conditional observations O01–O03). On 17 November 2026 we remediated
all five findings and replayed the same probes to prove each fix (Sections 11 and 18). A second release the same day
closed two of the three conditional observations for the threat of a stolen database password: the actor identity is
now proved to the database (O02) and audit events can no longer be forged by the web account (O03). The same
release added two-step sign-in for officers and auditors, review deadlines enforced by the database, a CSV export
for the auditor, e-mail notifications through a database outbox, and a continuous-integration workflow. We also
built a SQL-injection laboratory whose impact is demonstrated rather than assumed (Section 12) and rehearsed
two incidents, one of them a stolen service credential, run before and after the fix (Section 17).

3 Introduction and System Description
3.1 Scenario and why this system
A research office publishes grant calls. A researcher writes and submits a proposal. An officer assigns reviewers;
a reviewer scores the proposal (1–10) and writes private comments. The officer approves, with an amount, or
declines; approval reduces the call’s budget. An auditor can reconstruct who did what. We chose this system
from the assignment’s list of possibilities because it combines confidential content (unpublished research, private
reviews), integrity-critical money (a budget that must never be overspent), conflicts of interest (nobody reviews
their own proposal) and four clearly different categories of user, which is what makes least-privilege controls
meaningful.

3.3 Business rules enforced by the database, not only by PHP
A submitted proposal is immutable. A final review cannot change. A decision needs at least one completed review.
An award cannot exceed the requested amount or the remaining budget, and the budget only decreases. There is
at most one decision per proposal. A reviewer cannot be the applicant. A proposal can only be created in an open
call and only before its deadline. A reviewer cannot save or submit a review after its due date; only an officer can
move that date, and only forwards. Officers and auditors are not signed in until they present a second factor.

4 System Architecture
4.1 Runtime view
Every request follows the same ordered pipeline in src/Http/Kernel.php: security headers → session → route
match → CSRF (POST) → login → role permission → controller → database (RLS). The router is an explicit table
of 23 routes, and each names the permission it needs (for example decision.record or audit.read). Following
one button to the database is therefore a short, auditable path (Figure 15).

4.2 Separate database accounts, on purpose
Each request may open up to three PostgreSQL connections, each with a different account. db uses grants_
app for business transactions and presents a signed actor token for the transaction. auditDb uses a different
account, grants_audit_write, which has no table privilege and can only call audit_append(); it is a separate,
autocommit connection so that a denied audit event survives the rollback of the business transaction that was
refused. auditorDb uses the read-only grants_auditor account for the auditor screen and its CSV export. A
fourth account, grants_notifier, belongs to the notifier container that delivers e-mail (Section 13). The actor
identity is proved per transaction: the web process signs a short-lived token with a key only it holds, and the
database verifies the signature itself (Figure 3); a reused connection can never carry one user’s identity into the
next request, and a stolen database password alone yields no identity.

8 Authentication Design
8.1 Mechanism
Each person has an individual account (users), a role and an Argon2id password hash. Login uses a security-definer
helper, auth_find_credentials(email), because the runtime account has no privilege to select password_hash.
For researchers and reviewers a correct password opens the session at once: the session identifier is regenerated
(against fixation), a fresh CSRF token is issued and the event auth.login is recorded. Officers and auditors, and
anyone who enrolled, enter a pending state and must present a second factor first (Section 8.5). Logout is a POST
with a CSRF token and destroys the server-side session. On every later request the user row is read again, so a
disabled account or changed role takes effect immediately, not at next login.

8.4 Handling failed authentication: policy, trade-offs and remediation of F02–F04

10.1 Most important example: from three privileges to one door

a decision:

11 Vulnerability Analysis
11.1 Method and scope
Testing was performed only against the group’s own fictional system (assignment rules 5 and 6). On 11 November
2026 we attacked a separate disposable Docker stack (own project name, network, volumes, keys and passwords) on
localhost, in three layers: a black-box HTTP script, a TLS-verified authenticated HTTP harness (positive controls,
timing, throttling) and a restricted-SQL script that acts as an attacker who holds the runtime database credential.
A denial is interpreted only after a positive control proved that the account is valid and the resource exists. After
release 2 the restricted-SQL script was updated: it now models an attacker who holds only the database password
(claimed identity, forged token, forged audit event) as well as the original F01 probe. Administrative access was
used to prepare the lab, clear counters and collect evidence, never as the attack step. The campaign followed
the relevant areas of the OWASP Web Security Testing Guide; it is tailored, not a claim of full coverage. The
commands and per-family results are in Appendix B.

Security impact. A researcher who finds such a flaw obtains the identity of every account, including the officers
and the auditor: a confidentiality breach and a precise map for phishing or targeted login attacks. The same
injection could not read password hashes, the audit trail, other researchers’ proposals or any review comment,
and could not tamper with accounts, decisions or budgets. That ceiling is set by the privilege model of Sections 9
and 10, not by the application code, which is the point of defence in depth. (A smaller first demonstration on 11
November returned only the actor’s three own rows with the old two-column query; the lab was extended to show
real impact.)

12.3 Root cause
The statement text is built from user input, so the input can change the grammar of the statement (a quote, a
UNION, a comment marker). Blacklists and escaping functions do not fix this because the database still receives
one string in which code and data are mixed.

12.4 Remediation and why it prevents the vulnerability
   • Parameterized queries with server-side prepared statements. PDO is configured with ATTR_
     EMULATE_PREPARES=false: the statement is parsed by PostgreSQL first and the value travels separately,
     so it can only ever be a value. This is a structural fix, not a filter. As a side effect the server refuses stacked
     statements (A7–A9).
   • Server-side input validation. Titles, amounts (Money::parse), identifiers (route placeholders match
     digits only), dates and statuses are validated; LIKE wildcards in a search are escaped so % and _ are literal.
   • Secure error handling. A database error never reaches the browser: details go to a private log and the
     user sees a correlation reference.
   • Least-privileged application account and row-level security, which bounded the damage in A3–A9 even
     while the code was vulnerable.

12.5 Verification
The same nine payloads, run through the parameterized function, return 0 rows and no error; a legitimate title
containing an apostrophe (Children’s) returns 1 row. The regression test RLS search with an apostrophe returns
only authorized records (injection regression) keeps the legitimate case working, and the live application resisted
13 SQL-injection variants in its search box and audit filters with no foreign row, no error and no delay (pg_sleep
did not run). Evidence: docs/evidence/sqli-demo.txt (Appendix D). The terminal output of the second half,
the same nine payloads returning 0 rows, is Figure 20 (Appendix E).

13.2 Data at rest: field encryption and key management
Review comments are encrypted before they reach PostgreSQL with XChaCha20-Poly1305 (libsodium AEAD), so
a database dump, a backup or a DBA session shows only ciphertext. A random 24-byte nonce is used for every en-
cryption. The context (for example reviews.comments:42) and the header (version and key id) are authenticated
associated data: a ciphertext copied onto another row, or relabelled with another key id, fails to decrypt (tests
DATA review comments are encrypted at rest and bound to their row and key management. . . tampered headers).
Key management is a lifecycle, not a file. The keyring (secrets/field.key, mode 0600) holds one key per line
as <id>:<base64>; the first line is the active key, all lines can decrypt, and every stored value names its key
(v2:<id>:<payload>). The original single-key format (v1:) is still readable as key k1.

Principle          Implementation and evidence

                   the database
Separation         The key lives apart from the data it protects; the backup holds the ciphertext and the key backup is a
                   separate file (*.fieldkey.gpg) to be stored apart

                   audit event admin.rotate_field_key; nothing breaks in between (old values still decrypt)

13.3 Custody of the backup private key
Taking backups needs only the public key. The private key can read every backup, so scripts/backup-key.
sh puts a random passphrase on it, exports it for the restore team, and can delete it from the backup host.
backup-key-custody.txt shows, on a temporary copy of the keyring: decryption without the passphrase fails
(“No passphrase given”); after export and removal the host can still encrypt new backups but can no longer read
them (“No secret key”); and a restore on a clean workstation succeeds once the key file and passphrase are brought
by the custodians.

13.4 Minimising what an e-mail can leak
E-mail is the one channel that leaves our infrastructure. A message is queued by the database function notify_
enqueue() in the same transaction as the change; the function needs a valid actor token, lets a user queue a
message only about their own action (an officer who assigned a review, a reviewer who submitted one, an officer
who decided a proposal), chooses the recipient from the database relations and renders the text from a fixed
template. A message therefore says, for example, “A decision has been recorded on your proposal” with a link; it
never carries the decision, a title, an abstract, an amount or a score (test MAIL: the body contains none of them).
The unique key per (kind, subject, recipient) keeps anyone from using the function to flood a person. Delivery is
done by a separate container with its own account that can read only the outbox and the recipient’s address and
name (Figure 18); header-injection checks refuse a line break in any header value; SMTP credentials are sent only
over TLS and certificates are verified. The default transport writes .eml files, so nothing leaves the lab machine
unless an operator configures SMTP.

13.5 Data in transit
The browser connects over TLS 1.2/1.3 only (TLS 1.1 refused, HSTS one year, HTTP redirects to HTTPS).
The application connects to PostgreSQL with sslmode=verify-full against the database’s own certificate: the
connection is encrypted and the server’s identity is checked. The evidence file records protocol TLSv1.3 with
TLS_AES_256_GCM_SHA384; hostssl lines in pg_hba.conf refuse any non-TLS connection.

13.6 Honest limits
Proposal text is protected by access control, not by encryption; the PostgreSQL data directory is not encrypted
at volume level (disk encryption is a host responsibility); the lab certificates are self-signed; and the keyring, the
actor key, the private backup key and the passphrase file all start on one lab host, so the custody separation is
demonstrated, not enforced by the environment.

14.2 Answering who, what, when, which resource, and whether it succeeded
Each row of audit_events carries: who (actor_id, actor_role, the role at that moment); what (action);
when (occurred_at, wall-clock UTC, not the transaction start); which resource (resource_type, resource_id);
outcome (success, denied, failure); plus a per-request correlation_id, the source_ip, actor_verified
(proved by a token, or only named) and a small details document (identifiers, reasons, amounts, never proposal
text or comments; test no proposal text or review comment ever enters the audit trail).

14.3 Design and justification
   • Success events commit with the change (same transaction), so a change without its record, or a record
     without its change, is impossible; for awards the database function writes the event itself.
   • One door, two accounts (Figure 12). Events are written only through audit_append(). The web account
     has no privilege on the table; an event that names an actor needs a valid actor token for that actor, and the
     role is read from users. Events with no authenticated actor (failed sign-ins, throttling, CSRF rejections) and
     refusals are written by a separate account, grants_audit_write, which has no table privilege; the database
     flags them actor_verified=false, and the auditor screen shows “(unverified)”. A forged “success” for a
     decision or a deletion cannot be written without proof (closes O03).
   • Denials and authentication outcomes use a separate autocommit connection, so they persist when
     the refused business transaction rolls back (test a denied action is recorded although its transaction rolled
     back).
   • Append-only: nobody holds UPDATE, DELETE or TRUNCATE; triggers refuse them even for the schema
     owner.
   • The auditor reads a view (audit_timeline) through a read-only account; the page filters by outcome,
     action, resource and request id, shows no content, and offers a CSV export of the same filtered view (at
     most 5 000 rows, formula-neutralised for spreadsheets, a server-chosen file name); reading and exporting are
     themselves audited (audit.view, audit.export).
   • Threshold events are written once per crossing, so an attacker cannot use the audit trail as a flood
     target.

18.3 Limits of this assessment
The tests are bounded lab exercises on fictional data, not a certification. Timing was measured locally, without
network jitter. A distributed guessing attack against one researcher or reviewer account is detected, not prevented
(privileged roles also need a second factor, which is not phishing-resistant). TLS certificates are self-signed; e-mail
goes to files in the lab. A Docker administrator is trusted. Patch status: the 8 (web) and 5 (db) pending package
upgrades were applied on 17 November by rebuilding with pulled base images (now 0 and 0), but nothing keeps
them current automatically. The system is single-node and was not load-tested: with each request able to use two
runtime connections and a limit of 30, roughly 15 simultaneous requests is the ceiling. All key material, including
the actor key, starts on one lab host. A compromise of the web process, which holds the actor key, is not contained
by the database.

20 Conclusion
The project demonstrates the whole security process of the assignment on one realistic system. The design puts
integrity rules in the database, authorization in two independent layers and secrets under a documented key
lifecycle. The attack phase found real weaknesses – a partial-award path, an account-lockout denial of service, a
timing gap, missing throttling, a missing header, and two trust boundaries (a self-asserted identity and a writable
audit trail) – and, as the assignment requires, each was explained by its root cause and impact, fixed, and verified
by replaying the same probe; the stolen-credential incident was run before and after the fix. The SQL-injection
laboratory showed both the damage an injection can do and how privileges limit it. The two incidents show what
the evidence can and cannot prove, and name the controls that held and the ones that did not.
What we would claim, and no more: the delivered application resisted every attack we tried within a bounded
scope, the database refuses what the roles may not do even when the application is bypassed, and a lost database
can be restored with its privileges and encrypted content. What remains is documented and prioritized: the web
process that holds the actor key, phishing-resistant authentication for every role, tamper-evident audit and log
shipping, patch cadence and load behaviour.

-- HMAC-SHA256 (RFC 2104) from the built-in sha256(): no extension needed. Checked against RFC 4231 in tests/owner_guards.sql.
CREATE OR REPLACE FUNCTION hmac_sha256(p_key bytea, p_msg bytea) RETURNS bytea
LANGUAGE plpgsql IMMUTABLE SET search_path = pg_catalog AS $$
DECLARE
    k bytea := p_key; ipad bytea; opad bytea; i integer;
BEGIN
    IF length(k) > 64 THEN k := sha256(k); END IF;
    k := k || decode(repeat(’00’, 64 - length(k)), ’hex’);
    ipad := k; opad := k;
    FOR i IN 0..63 LOOP
        ipad := set_byte(ipad, i, get_byte(k, i) # 54);    -- 0x36
        opad := set_byte(opad, i, get_byte(k, i) # 92);    -- 0x5c
    END LOOP;
    RETURN sha256(opad || sha256(ipad || p_msg));
END $$;

-- The user id proved by a token, or NULL. Format v1.<uid>.<exp epoch>.<nonce hex>.<hmac hex>.
CREATE OR REPLACE FUNCTION actor_verify_token(p_token text) RETURNS bigint
LANGUAGE plpgsql STABLE SECURITY DEFINER SET search_path = grants, pg_temp AS $$
DECLARE
    parts text[]; k bytea; now_s double precision := extract(epoch FROM clock_timestamp());
    msg bytea; expected bytea;
BEGIN
    IF p_token IS NULL OR p_token = ’’ THEN RETURN NULL; END IF;
    parts := string_to_array(p_token, ’.’);
    IF array_length(parts, 1) IS DISTINCT FROM 5 OR parts[1] <> ’v1’
        OR parts[2] !~ ’^[0-9]{1,18}$’ OR parts[3] !~ ’^[0-9]{1,12}$’
        OR parts[4] !~ ’^[0-9a-f]{8,64}$’ OR parts[5] !~ ’^[0-9a-f]{64}$’ THEN
         RETURN NULL;
    END IF;
    -- short-lived: it must not have expired, and cannot claim more than 10 minutes of life
    IF parts[3]::bigint < now_s OR parts[3]::bigint > now_s + 600 THEN RETURN NULL; END IF;
    SELECT secret INTO k FROM actor_key WHERE id = 1;
    IF k IS NULL THEN RETURN NULL; END IF;
    msg := convert_to(format(’v1|%s|%s|%s’, parts[2], parts[3], parts[4]), ’UTF8’);
    expected := hmac_sha256(k, msg);
    -- compare the HMACs of both values (equal-time comparison pattern)
    IF hmac_sha256(k, expected) = hmac_sha256(k, decode(parts[5], ’hex’)) THEN
         RETURN parts[2]::bigint;
    END IF;
    RETURN NULL;
END $$;

-- The only way to write an audit event (apart from SECURITY DEFINER business functions such as record_decision).
CREATE OR REPLACE FUNCTION audit_append(
    p_action text, p_resource_type text, p_resource_id bigint, p_outcome text, p_details jsonb,
    p_correlation uuid, p_ip inet, p_claimed_actor bigint DEFAULT NULL, p_token text DEFAULT NULL)

    v_id bigint;

        RAISE EXCEPTION ’audit details are limited to 4000 characters’ USING ERRCODE = ’check_violation’;

        END IF;

    ELSE

        -- events that happen without an authenticated actor, or refusals.
        IF NOT pg_has_role(session_user, ’grants_audit_writer’, ’member’) THEN
            RAISE EXCEPTION ’an audit event needs a valid actor token’ USING ERRCODE = ’insufficient_privilege’;
        END IF;
        IF NOT (p_action ~ ’^(auth|request)\.’ OR p_outcome = ’denied’) THEN
            RAISE EXCEPTION ’this kind of event needs a verified actor’ USING ERRCODE = ’insufficient_privilege’;

    VALUES (v_actor, v_role, p_action, p_resource_type, p_resource_id, p_outcome, p_correlation, p_ip,
            coalesce(p_details, ’{}’::jsonb), v_verified)
    RETURNING id INTO v_id;
    RETURN v_id;
END $$;

        RAISE EXCEPTION ’the proposal is no longer under review’ USING ERRCODE = ’check_violation’;
    END IF;

    -- Moving a deadline: a grants officer only, only later, and nothing else changes in the same statement.
    IF NEW.due_at IS DISTINCT FROM OLD.due_at THEN
        IF v_role IS DISTINCT FROM ’officer’ THEN
            RAISE EXCEPTION ’only a grants officer can change a review deadline’ USING ERRCODE = ’check_violation’;
        END IF;
        IF NEW.due_at IS NULL OR (OLD.due_at IS NOT NULL AND NEW.due_at <= OLD.due_at) THEN
            RAISE EXCEPTION ’a review deadline can only be extended’ USING ERRCODE = ’check_violation’;
        END IF;
        IF (NEW.score, NEW.comments_enc, NEW.status) IS DISTINCT FROM (OLD.score, OLD.comments_enc, OLD.status) THEN
            RAISE EXCEPTION ’a deadline change cannot also change the review’ USING ERRCODE = ’check_violation’;
        END IF;
        RETURN NEW;
    END IF;
    -- An officer has no business editing a review’s content (the policy lets officers reach open reviews only to extend them).
    IF v_role = ’officer’ THEN
        RAISE EXCEPTION ’officers can only extend the deadline of a review’ USING ERRCODE = ’check_violation’;
    END IF;

    -- The reviewer’s work closes at the deadline (an officer can extend it first).
    IF OLD.due_at IS NOT NULL AND clock_timestamp() > OLD.due_at
        AND (NEW.status = ’submitted’ OR NEW.score IS DISTINCT FROM OLD.score OR NEW.comments_enc IS DISTINCT FROM OLD.comments_enc) THEN
         RAISE EXCEPTION ’the review deadline has passed’ USING ERRCODE = ’check_violation’;
    END IF;
    IF NEW.status = ’submitted’ THEN
         NEW.submitted_at := now();
    END IF;
    RETURN NEW;
END $$;

CREATE OR REPLACE FUNCTION mfa_require_self(p_user bigint) RETURNS void
LANGUAGE plpgsql STABLE SECURITY DEFINER SET search_path = grants, pg_temp AS $$
BEGIN
    IF p_user IS NULL OR current_actor_id() IS DISTINCT FROM p_user THEN
        RAISE EXCEPTION ’a valid actor token for this user is required’ USING ERRCODE = ’insufficient_privilege’;
    END IF;
END $$;

CREATE OR REPLACE FUNCTION mfa_state(p_user bigint)
RETURNS TABLE (enrolled boolean, secret_enc text, last_step bigint)
LANGUAGE plpgsql STABLE SECURITY DEFINER SET search_path = grants, pg_temp AS $$
BEGIN
    PERFORM mfa_require_self(p_user);
    RETURN QUERY SELECT u.totp_enrolled_at IS NOT NULL, u.totp_secret_enc, u.totp_last_step FROM users u WHERE u.id = p_user;
END $$;

-- Enrol once. A second enrolment is refused (an operator resets with scripts/mfa-reset.sh).
CREATE OR REPLACE FUNCTION mfa_enroll(p_user bigint, p_secret_enc text, p_code_hashes text[]) RETURNS void
LANGUAGE plpgsql SECURITY DEFINER SET search_path = grants, pg_temp AS $$
BEGIN
    PERFORM mfa_require_self(p_user);
    IF EXISTS (SELECT 1 FROM users WHERE id = p_user AND totp_enrolled_at IS NOT NULL) THEN
        RAISE EXCEPTION ’multi-factor authentication is already enrolled for this account’ USING ERRCODE = ’check_violation’;
    END IF;
    IF p_secret_enc IS NULL OR p_secret_enc !~ ’^v[12]:’ THEN
        RAISE EXCEPTION ’the secret must be stored encrypted’ USING ERRCODE = ’check_violation’;
    END IF;
    UPDATE users SET totp_secret_enc = p_secret_enc, totp_enrolled_at = now(), totp_last_step = 0 WHERE id = p_user;
    DELETE FROM mfa_recovery_codes WHERE user_id = p_user;
    INSERT INTO mfa_recovery_codes (user_id, code_hash) SELECT p_user, h FROM unnest(p_code_hashes) AS h;
END $$;

-- Atomic replay protection: a step is accepted once, and never an older one.
CREATE OR REPLACE FUNCTION mfa_accept_step(p_user bigint, p_step bigint) RETURNS boolean
LANGUAGE plpgsql SECURITY DEFINER SET search_path = grants, pg_temp AS $$
BEGIN
    PERFORM mfa_require_self(p_user);
    UPDATE users SET totp_last_step = p_step WHERE id = p_user AND totp_last_step < p_step;
    RETURN FOUND;
END $$;

CREATE OR REPLACE FUNCTION mfa_recovery_hashes(p_user bigint) RETURNS TABLE (id bigint, code_hash text)
LANGUAGE plpgsql STABLE SECURITY DEFINER SET search_path = grants, pg_temp AS $$
BEGIN
    PERFORM mfa_require_self(p_user);
    RETURN QUERY SELECT c.id, c.code_hash FROM mfa_recovery_codes c WHERE c.user_id = p_user AND c.used_at IS NULL ORDER BY c.id;
END $$;

CREATE OR REPLACE FUNCTION mfa_consume_recovery(p_user bigint, p_id bigint) RETURNS boolean
LANGUAGE plpgsql SECURITY DEFINER SET search_path = grants, pg_temp AS $$
BEGIN
    PERFORM mfa_require_self(p_user);

C.2d E-mail outbox (database/09_notifications.sql, enqueue function)

CREATE OR REPLACE FUNCTION notify_enqueue(p_kind text, p_ref_id bigint, p_base_url text) RETURNS integer
LANGUAGE plpgsql SECURITY DEFINER SET search_path = grants, pg_temp AS $$
DECLARE
    v_actor bigint := current_actor_id();
    v_role text    := current_actor_role();
    r       reviews%ROWTYPE;
    pr      proposals%ROWTYPE;
    n       integer := 0;
BEGIN
    IF v_actor IS NULL OR v_role IS NULL THEN
        RAISE EXCEPTION ’a valid actor token is required’ USING ERRCODE = ’insufficient_privilege’;
    END IF;
    IF p_base_url !~ ’^https?://[A-Za-z0-9.-]{1,100}(:[0-9]{1,5})?$’ THEN
        RAISE EXCEPTION ’the base address is not a plain http(s) origin’ USING ERRCODE = ’check_violation’;
    END IF;

    IF p_kind = ’review_assigned’ THEN
        SELECT * INTO r FROM reviews WHERE id = p_ref_id;
        IF NOT FOUND OR v_role <> ’officer’ OR r.assigned_by <> v_actor THEN
            RAISE EXCEPTION ’you can only notify about a review you assigned’ USING ERRCODE = ’insufficient_privilege’;
        END IF;
        INSERT INTO notifications (to_user_id, kind, ref_type, ref_id, subject, body)
        VALUES (r.reviewer_id, p_kind, ’review’, r.id, ’A proposal has been assigned to you for review’,
                format(E’A proposal has been assigned to you for review.%s\n\nSign in to read it: %s/reviews/%s\n\nThis message contains no proposal details.’,
                       CASE WHEN r.due_at IS NULL THEN ’’ ELSE E’\nReview due: ’ || to_char(r.due_at AT TIME ZONE ’UTC’, ’YYYY-MM-DD’) END,
                       p_base_url, r.id))
        ON CONFLICT DO NOTHING;
    ELSIF p_kind = ’review_submitted’ THEN
        SELECT * INTO r FROM reviews WHERE id = p_ref_id;
        IF NOT FOUND OR v_role <> ’reviewer’ OR r.reviewer_id <> v_actor OR r.status <> ’submitted’ THEN
            RAISE EXCEPTION ’you can only notify about a review you submitted’ USING ERRCODE = ’insufficient_privilege’;
        END IF;
        INSERT INTO notifications (to_user_id, kind, ref_type, ref_id, subject, body)
        VALUES (r.assigned_by, p_kind, ’review’, r.id, ’A review has been submitted’,
                format(E’A reviewer has submitted a review on a proposal you assigned.\n\nSign in to read it: %s/officer/proposals/%s\n\nThis message contains no proposal details.’,
                       p_base_url, r.proposal_id))
        ON CONFLICT DO NOTHING;
    ELSIF p_kind = ’decision_recorded’ THEN
        SELECT * INTO pr FROM proposals WHERE id = p_ref_id;
        IF NOT FOUND OR v_role <> ’officer’ OR NOT EXISTS (SELECT 1 FROM decisions d WHERE d.proposal_id = pr.id AND d.decided_by = v_actor) THEN
            RAISE EXCEPTION ’you can only notify about a decision you recorded’ USING ERRCODE = ’insufficient_privilege’;
        END IF;
        INSERT INTO notifications (to_user_id, kind, ref_type, ref_id, subject, body)
        VALUES (pr.owner_id, p_kind, ’proposal’, pr.id, ’A decision has been recorded on your proposal’,
                format(E’A decision has been recorded on your proposal.\n\nSign in to read it: %s/proposals/%s\n\nThis message does not contain the decision.’,
                       p_base_url, pr.id))
        ON CONFLICT DO NOTHING;
    ELSE
        RAISE EXCEPTION ’unknown notification kind’ USING ERRCODE = ’check_violation’;
    END IF;
    GET DIAGNOSTICS n = ROW_COUNT;
    RETURN n;
END $$;

Appendix H – Glossary

                                               Table 46: Glossary of terms

    Term                     Meaning in this report
    AEAD                   Authenticated encryption with associated data: encrypts and detects tampering; the
                           associated data (here the key id and the row) is authenticated but not stored twice
    Argon2id               Memory-hard, salted password-hashing function (RFC 9106); here 64 MiB, 4 passes, 1
                           lane
    Append-only            A table that can be inserted into but never updated, deleted or truncated (enforced by
                           privileges and triggers)
    Actor token            v1.<id>.<expiry>.<nonce>.<HMAC-SHA256>: proof, signed with secrets/actor.key,
                           that the web process acts for a user; verified by the database. The old app.user_id
                           claim is ignored
    Audit writer           The account grants_audit_write: no table privilege, can only call audit_append() for
                           events without an authenticated actor or for refusals
    Attack surface         The set of places where an attacker can interact with the system
    BYPASSRLS              Role attribute that skips row-level security; only the read-only backup account has it,
                           because pg_dump requires it
    Column-level privilege A GRANT on named columns only (for example SELECT on users without
                           password_hash)
    Correlation id         Random identifier written on every audit event of one HTTP request
    CSP / HSTS / COOP Browser security headers: Content-Security-Policy, HTTP Strict-Transport-Security,
    / CORP                 Cross-Origin-Opener-Policy, Cross-Origin-Resource-Policy
    CSRF                   Cross-site request forgery; countered by a synchronizer token in every state-changing
                           form
    Defence in depth       Independent layers, so that one failure does not expose the data
    DoS                    Denial of service; here the lockout of a victim (F02) or exhaustion of Argon2id memory
                           (F04)
    GR001                  Custom SQLSTATE used by record_decision() for a refused business rule; the
                           message carries the reason
    IDOR                   Insecure direct object reference: reading or changing another user’s record by guessing
                           its id
    Key id / keyring       Short identifier of an encryption key; the keyring file holds one key per line, the first line
                           being the active key
    Least privilege        Every account holds only the privileges it needs
    HMAC                   Keyed hash (RFC 2104); here HMAC-SHA256 signs actor tokens, computed in PHP and
                           verified in SQL
    MFA                    Multi-factor authentication; implemented as TOTP for officers and auditors
    NOLOGIN                Role that cannot connect; used for the schema owner and the privilege groups
    O01–O03                Conditional observations: hash helper (open, accepted), self-asserted actor and audit
                           insert trust (both closed for a stolen database password)
    Outbox                 A table of messages queued in the business transaction and delivered later by a separate
                           service
    pg_hba.conf            PostgreSQL client-authentication rules (who may connect, from where, with which
                           method)
    Replay protection      A one-time code is accepted once: the database stores the last accepted 30-second step
                           and refuses the same or an older one
    Prepared statement     A statement parsed by the server before the values are sent; with
                           ATTR_EMULATE_PREPARES=false the input can only be a value
    RLS                    Row-level security: policies that filter or refuse rows per actor
    SCRAM-SHA-256          Password-based challenge-response authentication of PostgreSQL clients
    SECURITY               A function that runs with its owner’s privileges; used for narrow, audited doors (login
    DEFINER                helper, record_decision(), throttle functions)
    SQLSTATE               Five-character PostgreSQL error code; 42501 = insufficient privilege, 23514 = check
                           violation
    STRIDE                 Threat categories: spoofing, tampering, repudiation, information disclosure, denial of
                           service, elevation of privilege
    TLS verify-full        Encrypted connection that also checks the server certificate against the host name
    TOTP                   Time-based one-time password (RFC 6238): HMAC-SHA1 of the current 30-second
                           step, 6 digits, produced by an authenticator app
    Trust boundary         Line across which data or control passes between components of different trust
    UNION injection        Appending a second SELECT to a vulnerable query to read other tables
    WAL                    Write-ahead log; continuous archiving of it would allow point-in-time recovery
                           (recommended, not implemented)
